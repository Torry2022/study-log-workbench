# Agent 补读与回答结束修正

本批修改实验路径的实际执行和来源管理，不增加模型、依赖或调用预算，不改默认能力开关。个人日志、问题和响应只保存在忽略目录。

## 后续排查：补查请求状态与重复生成

复查上一轮五次发生补读的问答，三次的最终答案使用了初始片段之外的相关原文，另两次没有证实补读带来必要的新依据。它们在读取前已经生成约一千至两千字的候选正文及引文，第一步各耗约 6—9 秒。因此进行了缩短首段输出的隔离对照，没有直接把协议改造迁入产品。

三个候选均未采用：只提交缺口时，固定检查中的四次充分材料与四次必要补读均通过，首段输出明显缩短，但宽泛对比从一次回答变为多次补读与兜底生成；保留简短原文锚点仍未守住该边界；再保留上一轮请求状态，也未消除首次补读的必要性问题。这些结果说明，去掉正文不能直接视为等价优化。未继续运行以该条件通过为前提的其他主题检查，失败候选与响应均留存，正式工具没有恢复直接 `read`，也没有引入题目条件或新的判断模型。

实际落地的是一个独立的状态修复：旧 `prepareStep` 重建原文输入时丢掉了补查目的，`lastTool` 还只保留并行组最后一项。现以 `previousEvidenceRequests` 保存上一组各项请求和结果，包含搜索目的、读取缺口、实际尝试日期与新增／恢复来源。它在整组完成后统一交接，未读到的日期不冒充已尝试，空查询不占用另一查询的结果，同日缺口仍共享读取。这里只记录执行经过，不证明材料充分或模型判断正确。原生 `answer`、引用校验、调用上限和默认开关不变；补读前的候选正文仍保留。

新增状态断言先在旧代码复现三项失败，覆盖同日多个缺口、并行命中与空查询、同编号原文恢复；修复后问答及通用主题 278 项通过。首次修改后的两项测试期望误用了另一条合成文案，已按实际发送参数纠正，未降低断言。类型检查、生产构建、MCP 60 项／1 原 Windows 权限跳过，以及实际入口和 Chromium／WebKit 浅深色、桌面／手机 22 组通过；已查看深色桌面回答与浅色手机保存失败截图，隔离源资料未变。

## 后续排查：表述边界与等待

继续检查补读决策重构后的十五轮回放，仅修正有代码依据的两项责任问题：

- **无日志与未读完没有明确区分。** 完整范围读取已返回全部记录，但回答仍把其余日期描述为是否有记录未知。现在由程序计算完整范围内没有已保存日志的日期数量，普通生成与 Agent 状态共用。搜索、部分读取、失败、无效或缺失边界、来源改变均不作无记录判断。记录不存在与正文被截断或摘录分别处理；没有记录不等于没有学习。
- **同模型辅助请求未沿用显式思考配置。** 最慢的一轮没有补读，约 19.7 秒花在追问理解，返回简短 JSON 前产生了大量推理内容；主回答已关闭思考，理解请求却沿用提供方默认值。query 路由现将显式设置传给同模型的问答辅助请求，独立轻量模型、标题和其他 AI 功能不受影响。未设置时维持原行为。

另外两处是通用知识没有完整放进补充区、把特定代码检索场景的说明扩大为一般结论。当前提示和来源标题已经包含所需边界，旧的生成规则强化实验也未得到稳定收益。这次没有继续堆叠提示、关键词规则、判断模型或正文改写器；不能宣称这两项已解决。

## 后续修正：统一已知来源补读

在补读完成保护修正后继续排查充分材料多读。实际工具参数把用户所问的全部要点作为“缺口”，但相应依据已在初始原文中；原实现同时允许直接 `read`、摘录无法匹配触发读、`answer.unresolved` 触发读，后两者与直接读的前置要求不同。

现在只保留 `answer.unresolved` 这一条已知来源补读入口：同一次 SDK 调用先整理已有答案和具体缺口，再按登记来源执行读取。`search` 仍可查新线索，MCP 的 `read_log_range` 不变；模型不能提交新日期扩大读取范围。没有增加独立规划、Jev、模型调用阶段或预算，也没有加入题目、项目名、日期或专业词的条件分支。

整轮回放发现，上一版还把每条引用都附上逐字摘录作为接收条件，导致已有来源的回答被拒绝。现分开检查来源编号、锚点与结论：全部引用必须已提供；仅依据日志的非拒答至少有一个正文或记录元数据锚点可核对；额外失真的锚点不触发读取，也不证明结论错误或正确。全部锚点无效及未知来源仍拒绝。是否需要补读只看明确缺口，不能把摘录格式问题当作信息缺口。

### 对照与完整流程

- 最终固定输入对照：充分材料两题各重复两次，四次均一调用且无追加 MCP；必要补读两题各重复两次，四次均取得所问机制或条件，每次两次模型调用、一次补读。原多读案例约 14.758 秒降至本批两次约 6.495、7.042 秒；不把单批观测当稳定提速承诺。
- 预先固定的其他主题两题各一次，均一调用且无追加读取。它们是其他材料对照，不是外部盲测。
- 开启 Agent 的实际 `createRagQueryStream`、当前历史处理、真实本机 MCP 及授权资料回放：八个会话十五轮全部完成，二十七次上游调用，五轮执行 Agent 补读；明确范围的一轮继续由普通分页路径处理。逐轮检查核心任务和引用，三轮仍有表述问题：通用补充出现在指定段落之外、把特定检索场景泛化、完整枚举后却把未存记录的日期说成未知。后者未进入 Agent；不能将全部问题归因于本次补读，也不能将 done 当作全部正确。
- 总耗时中位 9.845 秒，范围 2.396—27.702 秒，五轮首正文超过 15 秒。最慢一轮的追问理解在首次响应前约 19.7 秒，另有补读加长回答的等待；未宣称普遍达到首字延迟目标。宽泛问题里部分“可能还有更多表述”的补读是否值得，仍需与回答长度和任务范围一起评价。
- 中间候选保留：统一入口但保留旧逐引用强校验的完整回放有三轮错误；取消锚点要求的简化候选虽减少等待，却有一次必要补读被跳过，已弃用。最终保留有用的锚点约束，移除超出其证明能力的逐引用门槛，不靠放宽题目标准通过。

本批共九十八次供应商请求，九十六次收到用量；另两次中断请求保持未知，不记零。最终十五轮的二十七次均收到用量；这里记录请求与 token，不据此声称实际账单金额。所有中间结果留存，未覆盖失败或将其算入通过。

## 原因与修改

1. **取证与最终回答指令混用。** 旧 SDK 请求两处携带最终覆盖说明，其中包括材料不足时只回答已读部分的结束指令。旧失败记录中，工具存在且参数正确，模型却直接作答；没有证据表明 SDK 吞掉调用。现在取证使用单份结构化状态，保留剩余预算与可读日期，最终生成再使用最终覆盖说明。仅分开指令的隔离候选改善了四次缺口对照中的三次，仍有一次错误回答，不能把指令混用认定为唯一原因。
2. **未显式处理回答里的已知缺口。** 旧实现把模型正常结束的正文直接视为答案。现在模型通过 AI SDK 原生 `answer` 提交正文、来源锚点和缺口，代码处理已知来源的可执行补读；模型也可主动调用 `search`／`read`。这是同一次调用的动作选择，不增加预审或第二个判断器。正文直出不能绕过提交检查。
3. **补读后的证据视图重复。** 实际补读已成功，但旧片段与完整日块同时进入下一步，模型沿用了旧编号引用新正文。现在只在同一版本、小节身份匹配且内容确实包含时隐藏旧片段；登记身份继续保留。检查可把旧编号确定地归到已提供的完整原文，不做模糊匹配或跨版本拼接。
4. **结束状态由两处更新。** 新提交工具暴露出流消费与 SDK 回调竞争，第二步有效答案曾被提前标为步数耗尽。现在步数、并行工具结果和最终回答在 `onStepFinish` 统一决定。同一步的回答不能使用该步尚未返回的材料。

来源锚点只证明引用指向本轮已提供的原文，不证明论断必然成立。一个来源有有效锚点后，额外排版失真的锚点不使整篇回答失败；整条来源都无法核对时，必须补读或拒绝。模型仍可能遗漏缺口、错用相关背景或无谓读取，这些需要真实回答评价，不能由结构校验替代。

## 真实对照

固定使用同份初始检索结果、原文版本、模型与参数，对照旧 Agent 与候选。两道材料足够的对照各一次，两道旧缺口案例各重复两次；这是失败机制诊断，不是整体问答题库或盲测。

- 旧记录四次缺口均未补读。最终候选四次均读取了缺少的原文，答案包含所问机制或选择条件，逐项人工核对来源；每次两次模型请求，总耗时 6.060—8.956 秒。
- 充分材料的一题保持一次模型请求，约 6.100 秒；另一题仍多读两天，使用两次模型请求，约 14.758 秒。旧实现相同初始材料分别约 2.912、5.036 秒。这是明确的成本与等待回退，不能宣称稳定提速或达到默认启用条件。

- 中间严格逐条引文候选补读成功，但因附带图示的缩进差异被整篇拒绝，已改为按来源核对原文锚点。此前结果保留，不能只报告最终通过样本。
- 预设的其他主题留出题要求先通过充分材料无多读条件；该条件未通过，因此未运行。没有扩大调用次数或放宽启用门槛。

## 取证与正文交付协议重构

此前 `answer` 同时承担完整答案生成、来源检查和补读决策：补读前已写完整候选，补读后可能重写；不补读也必须等工具参数全部到齐才能显示。不能直接转发参数片段，因为同一步后面仍可能要求搜索、读取或报错。

当前以 `assess` 替代 `answer`，保留对已有材料的实质归纳，但不要求先写一份完整答复。参数为 `assessment`、逐字来源锚点 `evidence`、`unresolved` 和 `next`。`next=finish` 结束取证，剩余缺口用于最终答复；只有 `next=read` 才授权读取仍符合资格的已知来源。未说明的背景与需要继续读取的依据由此分开，不再看到缺口就自动读取。`search` 仍可查新线索，没有增加判断模型或额外规划阶段。

取证角色去除 Markdown 成文和通用知识小节的交付指令，防止同一阶段既要求交付正文又禁止正文。主模型最终通过现有流式回答通道交付，内部判断只作为待核对的组织线索，不是新增来源、事实证明或用户指令。它与缺口一起计入输入容量。来源、日期、取消、用量、失败分类和硬性预算仍由程序管理。

同时修正三个协议边界：接受原样渲染的标题／日期元数据作为身份锚点，仍拒绝虚构元数据；请求的已知来源已无读取资格时，保留判断与缺口并结束补查，而不把有效判断作为格式错误；最终生成复用 SDK 的 `modelContexts()`，不把已证明被同版本完整原文包含的旧片段重新放回输入。后者不做模糊合并，拼接片段不能证明被包含时仍保留，不能声称所有引用支持问题均已修复。

### 对照及未采用的中间实现

- 第一版仅把完整答复改成短材料归纳，尚未区分缺口与读取授权，也保留了取证角色中的成文指令。原十五轮新路径完成十二轮，旧路径完成十四轮；新路径有额外读取和直接输出正文的失败，未作为交付依据。它进一步说明不能只缩短一个输出字段。
- 分开读取授权、阶段指令并修正元数据锚点后，进行同批交替的十五轮对照。旧协议完成十五轮、二十八次调用；新协议完成十四轮、三十七次调用。范围读取调用为七／四次，均包含普通范围查询的一次读取。成功响应的首正文中位约八点六／六点八秒，总耗时中位约八点六／九点九秒；新路径存在失败，不能把这组速度数字当作质量通过。失败来自请求再次读取已读来源，后续已修正并补回归。
- 修正已知来源读取资格与输入容量后，原八会话十五轮再次完成，三十七次模型调用。首正文中位约七点一秒、总耗时约十点七秒，本批首正文均未超过十五秒。仅一轮执行 Agent 补读，另有一轮普通范围读取。这是后续单路径回放，不是另一次同期对照，也不是普遍耗时承诺；少读本身不证明回答正确。
- 固定充分材料两例各两次均不追加 MCP；固定必要补读两例各两次均取得缺失原文并给出所需机制、条件或否定。前者每次两次模型调用，后者每次三次，其中一次额外读取的收益未证实。另两例其他主题各一次均无补读、两次模型调用。逐项查看答案与实际原文后，仍有一处已读细节引用到旧拼接片段的问题，不能把取得原文记成引用全部正确。
- 进一步核对上述引用发现最终生成与 SDK 的原文视图不一致。用真实 MCP 和隔离合成资料新增前失败、后通过的入口断言，最终改为共用视图；原文不能证明包含旧拼接片段时不会强行合并，因此不能将这项修复扩写成语义引用问题全部解决。该项之后未再完整重跑付费十五轮，最终代码另跑全部专项和生产入口。

对照结论是：已实现取证与交付的职责拆分、实际正文流式输出和更明确的读取授权；尚未证明总耗时、调用成本及所有引用支持都改善。材料充分的短问题从一份完整提交变为一次短判断加一次正文调用，这是明确代价；不能只报告首正文变快。当前不叠加 Jev、额外路由模型、特定题目规则或生成后的措辞修补器。
