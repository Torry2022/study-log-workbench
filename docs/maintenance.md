# 实例运行与维护互斥

源码 Web 启动入口 `ops/run-web.mjs`、Docker standalone 的 `ops/serve.mjs` 与 Windows 包启动入口 在整个服务生命周期持有 `data/.instance-operation.lock`。初始化及维护使用相同锁，运行期间不能再次初始化、启动第二个 Web 进程或执行离线维护。只读检索服务不写原始学习记录；进行维护前仍应停止所有关联服务及外部编辑器。

锁的 `owner.json` 记录随机归属、操作名、进程号和开始时间，不含配置凭据。只释放当前进程建立且归属未变的锁；不会凭时间或 PID 自动清理遗留锁。

服务子进程正常退出后才释放锁。进程无法启动时释放已建立的锁；异常退出或强制终止保留锁，避免把可能未完成的操作当作正常停机。在 Linux 上，SIGTERM 转发给服务并等待其正常退出。Windows 的直接进程终止可能是强制结束，不能视作正常停机。本地包通过继承的私有 IPC 通道请求服务自身收尾：先停止 Web 接收新请求并等待在途操作，再停止检索，最后释放运行锁。Windows 桌面端请正常关闭工作台窗口；浏览器启动入口请点击“停止工作台”，待停止完成后关闭页面。不要用任务管理器结束进程代替。

遇到遗留锁时，先确认同一保存位置的 Web、检索进程和外部学习记录编辑均已停止，保留学习记录及配置的完整副本，核对有无随记恢复标记或未完成写入。确认状态后将锁目录移到副本中留作记录，再启动；不提供自动解锁或按进程号直接删锁的命令。记录的 PID 可能已经被系统复用。

Windows 启动入口还有当前账户下的启动锁，位于 `%LOCALAPPDATA%\StudyLogWorkbench\<程序目录标识>\launcher.lock`，与保存位置中的运行锁用途不同。若启动入口提示上次运行异常，也须先确认入口及其子服务全部停止，再保留该启动状态目录副本并处理锁。锁中的控制信息只用于本机当前账户，不要上传或分享。

初始化／子进程／锁归属测试已在 Windows 和隔离 Linux Node 22 容器执行；Linux 包括 SIGTERM 后等待异步收尾。Windows 包实际长流等待与离线归档恢复已有具名验证，这些结果不代表支持在线热备份。
